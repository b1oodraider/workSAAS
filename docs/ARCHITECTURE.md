# workSAAS — архитектура

Self-hosted помощник по поиску работы для 1–6 человек: оценка резюме, оценка
вакансий, подбор вакансий под резюме, генерация сопроводительных писем.
Работает на ноутбуке (4–8 ядер, 16 ГБ RAM, без GPU) или на VPS за $5–10/мес.

Документ описывает **почему** система устроена так, как устроена, и **куда**
класть новое. Если добавление фичи требует правки больше чем 2–3 «чужих»
файлов — это сигнал, что архитектура нарушена, а не что так и надо.

---

## 1. Ограничения, из которых всё следует

| Ограничение | Следствие |
|---|---|
| ≤ 6 пользователей, один процесс | Никаких Redis/Celery/Kafka/Postgres «на вырост». SQLite (WAL) + очередь задач в той же БД. |
| Слабое железо, нет GPU | LLM — внешний API по умолчанию. Локальная модель (Ollama/LM Studio) — опционально, через тот же интерфейс. Никаких ML-зависимостей (torch, sentence-transformers) в ядре. |
| Деньги на LLM ограничены | Кэш всех LLM-ответов, двухступенчатый подбор (дешёвый префильтр → LLM только для top-N), помесячный бюджет на пользователя, учёт стоимости каждого вызова. |
| Возможна блокировка сервисов по гео | Прокси настраивается отдельно для каждого провайдера LLM и для каждого источника вакансий. |
| Проект будет расти «фичами» | Вертикальные слайсы: одна фича = одна папка. Общее ядро не знает о конкретных фичах. |
| Разработка «навайбкоженная» с разными агентами | Жёсткие контракты (Pydantic-схемы на входе/выходе LLM), тесты с фейковым LLM, никакой магии в рантайме. |

## 2. Стек

- **Python 3.11+**, **FastAPI** (веб + API), **Jinja2** (серверный рендеринг,
  без сборки фронтенда, без npm).
- **SQLAlchemy 2.0** + **SQLite** (WAL). Миграции — **Alembic**. Переезд на
  Postgres = смена `DATABASE_URL`, код не меняется.
- **Pydantic v2** — все контракты: конфиг, выход LLM, входы источников.
- **anthropic** (официальный SDK) — основной LLM-провайдер.
  **OpenAI-совместимый** адаптер на `httpx` — для OpenRouter / DeepSeek /
  Ollama / LM Studio / vLLM и т.п.
- **pypdf**, **python-docx** — извлечение текста из резюме.
- Фоновые задачи — собственная очередь в таблице `jobs` + asyncio-воркер в
  том же процессе (для 6 человек этого достаточно с большим запасом).

Потребление: ~100–150 МБ RAM, CPU почти ноль в простое.

## 3. Слои и направление зависимостей

```
            ┌──────────────────────────────────────────┐
            │  web/  (FastAPI роуты, шаблоны)          │  ← интерфейсы
            │  bot/  (Telegram), cli.py                │
            └───────────────┬──────────────────────────┘
                            │ вызывает
            ┌───────────────▼──────────────────────────┐
            │  services/  (сценарии: загрузить резюме, │  ← use-cases
            │  запустить поиск, поставить анализ)      │
            │  features/  (LLM-фичи: схема+промпт)     │
            └──────┬──────────────┬────────────┬───────┘
                   │              │            │
         ┌─────────▼───┐  ┌───────▼─────┐  ┌───▼────────┐  ┌────────────┐
         │  llm/       │  │  sources/   │  │  jobs/     │  │  apply/    │  ← порты + адаптеры
         │  gateway,   │  │  hh, rss,   │  │  очередь,  │  │  отклики   │
         │  providers  │  │  manual     │  │  планировщик│  │  на сайтах │
         └─────────┬───┘  └───────┬─────┘  └───┬────────┘  └─────┬──────┘
                   └──────────────┼────────────┘
                          ┌───────▼────────┐
                          │  core/ models/ │  ← конфиг, БД, ORM, http, утилиты
                          └────────────────┘
```

Правила:

1. `core/` и `models/` не импортируют ничего из верхних слоёв.
2. `llm/`, `sources/`, `jobs/`, `apply/` не знают о конкретных фичах и веб-слое.
3. `features/*` не импортируют друг друга. Общее — в `features/_shared.py`
   или ниже по слоям.
4. `web/` и `bot/` не ходят в LLM, источники и `apply/` напрямую — только через
   `services/` или постановку задачи в очередь.
5. Долгие операции (LLM, сеть) **всегда** идут через очередь `jobs`.
   HTTP-запрос браузера только ставит задачу и показывает статус.

## 4. Ключевые абстракции (точки расширения)

### 4.1 LLM: `LLMProvider` → `LLMGateway` → `LLMTask`

```
LLMTask   — ЧТО спросить: имя, версия промпта, Pydantic-схема ответа,
            шаблоны system/user, max_tokens, effort.
LLMGateway— КАК спросить: выбор провайдера/модели по имени задачи (из конфига),
            рендер промпта, кэш, бюджет, учёт стоимости, валидация ответа.
LLMProvider— КУДА спросить: anthropic | openai_compat | fake.
```

- Провайдер реализует один метод:
  `async generate(req: LLMRequest) -> LLMResponse`, где `req` содержит
  JSON-схему ответа, а `LLMResponse` — сырой JSON + usage.
- Gateway по имени задачи находит маршрут в конфиге:
  ```toml
  [llm.routes.default]   provider="anthropic" model="claude-opus-5-5" effort="medium"
  [llm.routes.match]     provider="anthropic" model="claude-opus-5-5" effort="low"
  [llm.routes.cover_letter] provider="local" model="qwen2.5:7b"
  ```
  Так можно дешёвую модель поставить на массовый матчинг, а сильную — на
  сопроводительные, **без правки кода**. У маршрута могут быть `fallbacks` —
  резервные провайдеры, которые пробуются по очереди, если основной недоступен.
- У провайдера есть `price_multiplier` (наценка реселлера) — бюджет считается
  по реальной цене, а не по официальному прайсу.
- Перед рендером промпта все переменные проходят `neutralize()`: текст вакансии
  не может закрыть тег `</vacancy>` и выдать себя за инструкцию.
- **Кэш**: ключ = sha256(задача, версия промпта, провайдер, модель, итоговые
  тексты промптов). Одинаковая вакансия, проанализированная для двух друзей,
  оплачивается один раз. Изменили промпт → подняли `version` → кэш
  автоматически «протух».
- **Бюджет**: перед каждым некэшированным вызовом gateway проверяет сумму
  `llm_usage.cost_usd` пользователя за текущий месяц.
- **Отказы модели** (`stop_reason == "refusal"`) и невалидный JSON — типизированные
  исключения `LLMRefusal` / `LLMInvalidOutput`; очередь показывает их
  пользователю как понятную ошибку.

### 4.2 Фича = вертикальный слайс `features/<name>/`

```
features/resume_review/
    __init__.py      # FEATURE = AnalysisFeature(...)  — регистрация
    schema.py        # Pydantic-модель ответа LLM
    system.j2        # system-промпт
    user.j2          # user-промпт (переменные: resume, vacancy, params)
    view.html        # как показать результат (Jinja-partial)
```

`AnalysisFeature` описывает:
- `kind` — уникальное имя (оно же имя LLM-задачи и маршрута в конфиге);
- `subject` — на чём работает: `resume`, `vacancy` или `resume_vacancy`;
- `task` — `LLMTask` (схема + промпты + версия);
- `params_model` — Pydantic-модель пользовательских параметров (тон письма,
  язык…), из неё же строится форма;
- `view` — шаблон отображения.

Всё остальное — общее и написано один раз:
- универсальный обработчик задачи `analysis` грузит резюме/вакансию, рендерит
  промпт, вызывает gateway, сохраняет `Analysis(kind, output_json, …)`;
- страница резюме/вакансии показывает кнопки всех фич с подходящим
  `subject` и историю результатов, рендеря каждую через её `view`.

**Добавить новую LLM-фичу** (например, «подготовка к собеседованию»):
создать папку с 5 файлами и добавить одну строку импорта в
`features/__init__.py`. Ни миграций БД, ни правок роутов, ни правок очереди.

### 4.3 Источники вакансий: `JobSource`

```python
class JobSource(ABC):
    name, title, hint: str
    searchable: bool            # False для ручного ввода
    trusted: bool               # False, если текст пишут произвольные люди (Telegram, RSS, ручной ввод)
    enabled_by_default, checked_by_default: bool
    async def search(self, query: SearchQuery, limit: int) -> list[VacancyDraft]: ...
    async def fetch(self, external_id: str) -> VacancyDraft | None: ...  # полная карточка
    def external_id_from_url(self, url: str) -> str | None: ...          # импорт по ссылке
```

- `VacancyDraft` — нормализованная вакансия (заголовок, компания, зарплата,
  описание, url, `external_id`…). БД хранит только нормализованный вид +
  `raw_json` для отладки.
- Реестр источников заполняется из конфига: включён/выключен, прокси,
  параметры (регион hh, список RSS-лент…).
- Дедупликация по `(source, external_id)`; вакансии общие для всех
  пользователей (анализ вакансии кэшируется для всех).

Реализовано: `hh` (API → разбор сайта), `habr`, `trudvsem`, `superjob`,
`telegram` (публичные каналы), `rss`, `remotive`, `remoteok`, `manual`.
Каждый — один файл в `sources/` + строка в `sources/registry.py` + (необязательно)
секция в конфиге; у класса есть `enabled_by_default`, `checked_by_default`, `hint`.

Общие кирпичики для источников:
- `sources/web.py` — `PageFetcher`: вежливый HTTP с заголовками браузера и
  паузами на хост, headless-браузер (Playwright, опционально) и `AutoFetcher`,
  который переключается на браузер при капче; `fetch_json` для JSON-API;
  короткий кэш ответов (одна лента не скачивается заново для каждого запроса).
- `sources/jsonld.py` — разбор schema.org `JobPosting` (есть почти на всех
  сайтах вакансий); используется hh, Хабром и импортом по любой ссылке.
- `safe_map` / `as_str` / `as_dict` в `sources/base.py` — битый элемент
  чужих данных пропускается с записью в лог, а не роняет весь поиск.

Дедупликация: `vacancies.dedup_key` = нормализованные «компания|название».
Одна вакансия из нескольких источников склеивается в одну запись и оценивается
ИИ один раз. Каноническая копия берётся только из «доверенных» источников
(`JobSource.trusted`), чтобы пользовательский текст не подменял чужие вакансии.

### 4.4 Очередь задач `jobs/`

- Таблица `jobs(kind, payload_json, status, attempts, error, result_json…)`.
- Обработчики регистрируются декоратором `@job_handler("kind")`.
- Воркер — asyncio-цикл в процессе веб-сервера (или отдельно: `worker`
  команда CLI) с ограничением параллелизма (по умолчанию 2 — чтобы не
  упереться в rate-limit API и не душить слабый CPU при локальной LLM).
- Сбой процесса: задачи в статусе `running` при старте возвращаются в `queued`.
- Планировщик раз в минуту ставит задачи для сохранённых поисков, у которых
  подошло время (`interval_minutes`).

### 4.5 Подбор вакансий (pipeline)

```
Резюме ──LLM(resume_profile)──► Профиль: роли (с синонимами RU/EN и широкими названиями), навыки, грейд, поисковые запросы,
                                 желаемые зарплата/локация/формат
        │
SavedSearch(resume, источники, фильтры)
        │  job: search_run
        ▼
1. sources.search(запросы профиля)  → upsert в vacancies
2. prefilter (без LLM, мгновенно):  совпадение навыков/ключевых слов,
                                     жёсткие фильтры (зарплата, remote, стоп-слова,
                                     период публикации — для всех источников),
                                     старые вакансии получают меньший балл
3. top-N (N из конфига) → job: analysis(kind="match") для каждой
4. Страница «Подбор»: сортировка по LLM-оценке (или префильтру) ± поправка
   за оценку компании (до ±5), затем по дате публикации
```

Промпты не привязаны к IT: профиль, оценки и письма работают для любой профессии.

**Обратная связь и оценка компаний.** Пользователь ставит 👍/👎 оценке ИИ (при 👎 —
причина из `MATCH_VOTE_REASONS`) и отмечает, какой ответ дал работодатель
(`RESPONSE_QUALITY`); оба поля — в `user_vacancies`. `services/companies.py` считает
рейтинг компании на лету по данным всех пользователей экземпляра: доля ответов и
скорость (история статусов трекера), содержательность ответов, качество текстов
вакансий (`vacancy_review`), 👎 с причиной «компания». Сторонние отзывы не собираются.
Рейтинг — лёгкий аргумент: бейдж и поправка сортировки, без влияния на оценку ИИ и автоотклики.

Префильтр — интерфейс `Ranker`; нынешняя реализация — взвешенный поиск
ключевых слов. Если захочется эмбеддингов (локальная ONNX-модель), это новый
`Ranker`, остальной конвейер не меняется.

### 4.6 Автоотклики: `Applier` (`app/apply/`) и `services/autoapply.py`

`Applier` — отправка одного отклика на одном сайте от имени пользователя:

```python
class Applier(ABC):
    source = "hh"                 # JobSource.name вакансий, которые он обрабатывает
    title = "hh.ru"
    login_url, account_url         # для `worksaas site-login` и проверки входа
    session_domains = ("hh.ru",)   # какие cookies сохранять из браузера пользователя
    def is_ready(user_id) -> (ok, hint)
    async def apply(ApplyRequest) -> ApplyResult  # applied | skipped | failed | blocked
```

- `applied` — сайт подтвердил; `skipped` — сознательно не отправлено (анкета, отклик на сайте
  компании, уже откликались); `failed` — ошибка на этой вакансии (`transient` — повторить позже,
  `maybe_sent` — после нажатия «Отправить», засчитывается в лимиты); `blocked` — капча/выход из
  аккаунта: автоотклики пользователя встают на паузу.
- Сессии (Playwright `storage_state`) — `data_dir/sessions/<site>_<uid>.json`, права 0600,
  только cookies доменов сайта, в интерфейсе не показываются; методы `save_session`/`delete_session`
  базового класса. Браузер — через `core.http.chromium_launch_options` (прокси, свой Chrome).
- Реестр — `apply/registry.py::APPLIER_CLASSES`.

Сервис (сценарий целиком):

```
@periodic autoapply_tick ─► восстановление зависших «sending»
                         ─► plan(): лучшие совпадения (оценка ≥ порога, не «skip», без high red flags,
                            вакансия открыта в трекере), не больше дневного лимита
                         ─► job autoapply_prepare: письма через run_analysis("cover_letter",
                            use_preferences=False); подозрительное письмо → статус review
                         ─► next_to_send(): режим, часы, лимиты, интервал с разбросом
                            → атомарный захват строки → job autoapply_send (одна на пользователя)
job autoapply_send ─► перепроверка (пауза, часы, трекер) ─► Applier.apply (один отклик одновременно на весь сервер)
                   ─► applied: статус в трекере; blocked: пауза; failed ×N подряд: пауза
```

Статусы `applications`: queued → (review) → approved → sending → applied/skipped/failed; cancelled —
отказ пользователя. Жёсткие потолки — `[apply]` в конфиге, применяются и к ранее сохранённым настройкам.

## 5. Данные

| Таблица | Назначение |
|---|---|
| `users` | логин, хэш пароля (scrypt), админ, месячный бюджет $ |
| `resumes` | текст резюме (+ исходное имя файла), владелец |
| `vacancies` | нормализованные вакансии, общие; `unique(source, external_id)` |
| `user_vacancies` | статус вакансии для пользователя (new/saved/applied/interview/offer/rejected/hidden), оценка префильтра, трекер: история статусов, дата отклика, следующий шаг, отметки об уведомлениях; 👍/👎 оценке ИИ с причиной; тип ответа работодателя |
| `saved_searches` | резюме + источники + фильтры + период автозапуска |
| `analyses` | **универсальное** хранилище результатов фич: kind, resume_id?, vacancy_id?, params_json, output_json, модель, версия промпта |
| `jobs` | очередь задач |
| `llm_cache` | кэш ответов LLM по ключу |
| `llm_usage` | каждый вызов: пользователь, задача, модель, токены, $ , из кэша ли |
| `telegram_link_codes` | одноразовые коды привязки Telegram (15 минут) |
| `applications` | автоотклики: вакансия, резюме, статус, письмо, причина, время отправки, попытки |
| `autoapply_settings` | настройки автооткликов пользователя: режим, порог, лимиты, часы, пауза и её причина, счётчик неудач подряд |

Почему `analyses` универсальная, а не по таблице на фичу: новые фичи не
требуют миграций; выход валидируется Pydantic-схемой фичи при чтении.
Если какой-то результат понадобится фильтровать SQL-ем (например, оценку
матча), выносим поле в отдельную колонку (`analyses.score`) — это уже сделано
для оценок.

## 6. Конфигурация

- `config.toml` — структура (маршруты LLM, источники, лимиты). Пример:
  `config.example.toml`.
- `.env` — секреты: `WS_SECRET_KEY`, ключи провайдеров (имя переменной задаётся
  `api_key_env` у провайдера), `WS_TELEGRAM__BOT_TOKEN`, `WS_PROXY_URL`,
  ключи источников (`SUPERJOB_API_KEY`). Пример: `.env.example`.
- `[apply]` — потолки автооткликов для всех, прокси и селекторы страниц hh.ru;
  `data_dir` — где лежат сессии сайтов (`data/sessions/`).
- Любой параметр можно переопределить переменной окружения с префиксом
  `WS_` и `__` как разделителем уровней.

## 7. Веб-интерфейс

Серверный рендеринг, минимум JS (только автообновление статуса задачи).
Страницы: вход; резюме (список, загрузка, карточка с анализами); вакансии
(список с фильтрами, добавление вручную, карточка с анализами); подбор
(сохранённые поиски и результаты); задачи; расходы (своё потребление, для
админа — всех). Пользователи создаются админом через CLI — регистрации нет.

Главная (`/`): первые шаги, «пора действовать», лучшие совпадения, текущие задачи.
Админка (`/admin`): пользователи, бюджеты, здоровье источников и LLM.
Страница «Отклики» (`/tracker`) — воронка и напоминания.
Страница «Автоотклики» (`/autoapply`) — состояние и причина простоя, вход на сайты, настройки,
очередь с письмами, история.

### 7.1 Telegram-бот (`app/bot/`)

- `api.py` — минимальный клиент Bot API на httpx (long polling), экранирование HTML,
  фильтр, вырезающий токен из логов.
- `handlers.py` — команды и кнопки регистрируются декораторами `@command` / `@callback`;
  новая команда = одна функция. Пользователь определяется по chat_id привязанного чата,
  любые id из кнопок проверяются через `services` (`get_for_user`, `get_owned`).
- `jobs.py` — фоновые задачи, начатые из бота (анализ вакансии по ссылке, письма);
  результат они отправляют в чат сами.
- `digest.py` — дайджест новых сильных совпадений и напоминания трекера; строки
  «захватываются» условным UPDATE до отправки, поэтому два процесса не дублируют сообщения.
  Там же автоотклики: письмо на подтверждение (по сообщению на отклик, кнопки `aa`/`ax`/`au`),
  отчёты об отправке, уведомление о паузе (`ar` — продолжить, `ap` — пауза; команда `/autoapply`).
- `runner.py` — цикл опроса + периодические рассылки; запускается внутри веб-процесса
  или отдельно (`worksaas bot`). Один токен — один опрашивающий процесс.

`app/plugins.py::load_all()` импортирует все модули с обработчиками задач —
одинаково для веба, воркера, бота и тестов.

## 8. Безопасность

- Пароли — `hashlib.scrypt`, сессии — подписанная cookie (`SECRET_KEY`).
- Каждый доступ к резюме/вакансии/анализу/поиску проверяет владельца в сервисах
  (`get_owned`, `get_for_user`); кнопки бота проходят те же проверки.
  `tests/test_regressions.py` проверяет чужие id на всех маршрутах.
- Текст резюме и вакансий в промптах оборачивается в теги
  `<resume>…</resume>` / `<vacancy>…</vacancy>`, в system-промпте сказано,
  что это данные, а не инструкции (защита от prompt-injection из текстов
  вакансий).
- На VPS — только за reverse-proxy с HTTPS (Caddy — пример в README).
- Автоотклики: файлы сессий сайтов — как пароли (0600, только нужные домены, лимит размера при
  загрузке, удаляются при блокировке пользователя, в бэкап БД не входят). Письма для автооткликов
  пишутся без `<preferences>`, а письмо со ссылками/контактами не из резюме ждёт проверки
  пользователя — чтобы текст вакансии не мог заставить модель разослать лишнее.
  Браузер не уходит с доменов сайта (отклик на сайте работодателя — вручную).

## 9. Тестирование

- `FakeProvider` возвращает валидные по схеме заглушки — весь конвейер
  (очередь → gateway → кэш → сохранение → UI) тестируется без сети и денег.
- Источники тестируются на сохранённых фикстурах ответов.
- `pytest` запускается одной командой; CI не нужен, но легко добавляется.

## 10. Проверка качества

- `tests/test_architecture.py` разбирает импорты всех модулей `app/` и падает при
  нарушении слоёв (раздел 3) или импорте одной фичи из другой.
- `tests/test_migrations.py` — модели совпадают с миграциями, а обновление
  заполненной базы не теряет данные.
- Ошибки для пользователя — наследники `app.core.errors.UserError`: воркер показывает
  их текст как есть и повторяет только `retryable`.

`.claude/agents/` — агенты-критики для Claude Code: `code-reviewer`, `security-auditor`,
`architecture-guard`, `prompt-critic`, `ux-reviewer`, `test-critic`, `product-critic`.
После заметного изменения запускаются подходящие (см. `CLAUDE.md`); их находки
исправляются до коммита.

## 11. Рецепты расширения

| Хочу | Что делать |
|---|---|
| Новую LLM-фичу | `features/<name>/` (5 файлов) + строка в `features/__init__.py` |
| Поменять промпт | правка `.j2` + `version` в `__init__.py` фичи |
| Другую модель для фичи | `[llm.routes.<kind>]` в `config.toml` |
| Новый LLM-провайдер | класс в `llm/providers/`, регистрация в `llm/providers/__init__.py` |
| Новый источник вакансий | файл в `sources/` + регистрация + секция `[sources.<name>]` |
| Новую фоновую операцию | функция с `@job_handler("kind")` в `services/<модуль>.py`; новый модуль добавить в импорт `services/__init__.py` |
| Периодическое действие | функция с `@periodic` (из `jobs/scheduler.py`) в модуле сервиса |
| Новую страницу | роутер в `web/routes/` + шаблон |
| Команду бота | функция с `@command("name", "описание")` в `bot/handlers.py` |
| Кнопку бота | функция с `@callback("prefix")`; данные кнопки ≤ 64 байт |
| Автоотклики на новом сайте | класс-наследник `Applier` в `apply/<site>.py` + строка в `APPLIER_CLASSES`; селекторы — в конфиг |
| Postgres | `WS_DATABASE_URL=postgresql+psycopg://…`, `alembic upgrade head` |
